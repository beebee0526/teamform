# 구현 계획

## 1. 파일 구조
```
streamlit_app.py   화면(로그인, 학생 화면, 관리자 화면). key는 공고 2.7절 그대로
rules.py           규칙 함수(순수 함수): 지원 검사, 필수 포함 역할 자리, 배정안 검사 5가지, 백트래킹 배정, 불가능 이유
services.py        DB 트랜잭션: 로그인, 명단 올리기, 지원, 투표(승인 직전 재검사), 마감, 확정
ai.py              오픈라우터 호출(스트리밍, 모델당 120초 전체 제한), 1→2→3차 대체, 배경 스레드 작업
db.py              .env/Secrets 읽기, 연결 풀, schema.sql 실행
schema.sql         tf_ 테이블과 제약
tests/             연습용 시나리오 3개 자동 확인(run_scenarios.py), 명단 CSV
.github/workflows/keepalive.yml  매일 DB 질의(일시정지 방지)
```

## 2. 단계
1. DB 스키마(`schema.sql`) — 유일성 제약, 역할 check, 대기 지원 1개 부분 유일 인덱스, RLS
2. 규칙 함수(`rules.py`) — `check_join`을 지원과 승인 직전 재검사가 함께 씀
3. 서비스(`services.py`) — 쓰는 동작은 `pg_advisory_xact_lock`으로 차례로 처리
4. 화면(`streamlit_app.py`) — 콜백(on_click)으로 동작 → 결과를 session_state에 저장 → fragment가 다시 그림
5. AI(`ai.py`) — 먼저 백트래킹으로 가능 여부 확인 → AI 1~3차 → 실패 시 백트래킹 결과
6. 검증 — 연습용 시나리오 3개의 모든 단계 첫 단어 확인, 확정 뒤 규칙 확인, 120초 제한 확인
7. 배포 — Streamlit Community Cloud(비공개 저장소 연결, 앱 공개 설정), Secrets 입력

## 3. 설계 결정
| 문제 | 결정 | 이유 |
|---|---|---|
| 다른 사람의 변경 보기 | `st.fragment(run_every=3)` | 3초마다 그 부분만 다시 그림(5초 이하) |
| 같은 팀에 대기 지원 여럿 | 마지막 찬성 때 `check_join` 재검사 | 투표가 끝난 순서대로 처리 |
| 마지막 자리 동시 입력 | advisory lock + `(team_id, slot_no)` 기본 키 | 먼저 도착한 학생만 기록 |
| AI 응답이 늦음 | 스트리밍 + 별도 스레드, 모델마다 120초 전체 시간 | 천천히 오는 응답도 끊음 |
| AI 배정 중 화면 | 배경 스레드 + 1초마다 "N차 모델 응답 기다리는 중 (경과 초)" | 화면이 다시 그려져도 작업이 끊기지 않음 |
| 3차까지 실패 | 백트래킹(빈 팀 대칭 제거, 가지치기) | 모든 경우를 따져 규칙을 지키는 배정을 찾음 |
| DB 연결 | `psycopg_pool.ConnectionPool`을 `st.cache_resource`로 하나만 | 질의마다 연결을 새로 만들지 않음 |
| Supabase 풀러 | `prepare_threshold=None` | transaction 풀러는 prepared statement를 지원하지 않음 |
